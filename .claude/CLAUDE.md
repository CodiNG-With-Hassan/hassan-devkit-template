The Claude skill stubs under `.claude/skills/` (the house skills, `add-error-code` among them, plus
every skill of the `mattpocock-skills` devDependency) are generated by `hassan-devkit claude:install`
on every install and gitignored through its managed block — never commit one; Renovate bumps the
`mattpocock-skills` tag. The hooks in `.claude/settings.json` are the devkit's managed dispatcher
entries (`claude:hook pre-bash | post-edit`): the Bash guards and format-on-edit described in the
house standards above — never edit them by hand.

This is the starting point of a new project, not a product: every name in it is a placeholder
(`template`, the ticket key `TPL`, the `tpl-i18n` package, the ports) that the project setup
renames, and the two start pages exist only to prove the shell renders. Nx package-based pnpm
workspace: apps live in `apps/` (`api`, `web-admin`, `web-customer`), shared libraries in `libs/`
(as `workspace:*` packages, consumed as source). One `pnpm install` at the root covers everything.
`web-admin` is the staff (back-office) app, browser-only; `web-customer` is the customer site,
server-side rendered. Both ship in English and Dutch. Decisions: `docs/adr/`; the domain glossary
(`CONTEXT.md`) is written when the project has a domain.

## Docker

Project notes on top of the house rules (`pnpm docker:dev:up|down|logs`, managed `.env`):

- **Crashed dev server**: `backend`/`customer`/`admin` restart at most 3 times, then stay `Exited`
  (visible in `docker ps -a`) — read `pnpm docker:dev:logs`, fix the cause, run `pnpm docker:dev:up`
  again. The database restarts on its own.
- Restart one dev server: `pnpm docker:dev:restart-api|restart-customer|restart-admin`.
- Host ports are placeholders (API 3000, web-customer 4200, web-admin 4201, Postgres 5432, pgAdmin
  5050; slot n adds n × 10). A real project moves them clear of the other projects on the machine.
- A new workspace package goes into the `COPY` list of every dev Dockerfile (`docker/Dockerfile.dev`,
  `docker/Dockerfile.customer.dev`, `docker/Dockerfile.admin.dev`); a source-shared lib a web app
  compiles also goes into the `pnpm install --filter` list of that app's Dockerfile.
- There are no production images or deployment config: deployment is the project's own decision.

## Worktrees (parallel tickets)

The house rules cover the lifecycle (`pnpm worktree:create TPL-XX-Short-Title`, `env`,
`profiles`, `remove`, `prune`, `list`); full guide: `docs/WORKTREES.md`. Project specifics:

- Worktrees live under `../template-worktrees/<branch>/`; the GitHub issue in the branch name
  (`TPL-<n>` is issue `#<n>`) is assigned to you by `create`.
- **Profiles**: `api` (db, backend) is the mandatory default; `customer` = web-customer dev server
  (server-side rendering, the heaviest), `admin` = web-admin dev server, `extras` = pgAdmin (off
  everywhere, main checkout included). Docker memory is shared by every session — add a web
  profile only while verifying in a browser, remove it after.
- Live-spec `pnpm api:types` regenerates from **this worktree's** running API (`API_SPEC_URL`
  in `.env`); the API stamps the spec with its stack + branch and `fetch-spec.mjs` refuses one
  from another checkout.
- The dev servers reach the API through a `/api` proxy (`apps/<app>/proxy.conf.mjs`); the dev
  `environment.ts` uses a relative `apiUrl` on purpose — never hardcode a port in it.

## Backend conventions

- Feature modules live under `apps/api/src/<feature>/`; TypeORM entities live in the top-level
  `apps/api/entities/` directory (shared across modules, created with the first entity), not
  inside feature modules.
- The schema follows the entities (`synchronize: true`, ADR 0001); a step synchronize cannot do
  safely is idempotent SQL in `apps/api/src/migrations/`, awaited in `main.ts` before the app is
  created.
- Every route is served under the `/api` global prefix; Swagger UI is at `/api`, the spec at
  `/api-json`.
- Client-facing errors are `DomainException`s over the `ErrorCode` enum (ADR 0002) — constructing
  a Nest `HttpException` fails lint.

## Frontend conventions

- `web-customer` renders on the server: guard every `localStorage`, `window` and `document` access
  with `isPlatformBrowser`, and keep relative requests relative (the server-side render resolves
  them through `serverAbsoluteUrlInterceptor`). See `apps/web-customer/README.md`.
- App-agnostic UI (logo, theme and language switches, field errors, the `translateError` pipe)
  lives in `libs/web-ui`; an app keeps only what is its own.

## Linting & Formatting

Each app owns its own Prettier and ESLint config. Always defer to the standards of the app the file lives in — do not carry BE conventions into FE files or vice versa.

| Project | Path | Prettier | ESLint | Notable rules |
|---|---|---|---|---|
| API (NestJS) | `apps/api/` | `.prettierrc` | `eslint.config.mjs` | `singleQuote`, `trailingComma: "all"`; constructing a Nest `HttpException` is banned (ADR 0002) |
| Web Admin (Angular) | `apps/web-admin/` | `.prettierrc` | `eslint.config.js` (angular-eslint) | `printWidth: 100`, `singleQuote`, signal forms only |
| Web Customer (Angular, SSR) | `apps/web-customer/` | `.prettierrc` | `eslint.config.js` (angular-eslint) | same as web-admin |

Everything else uses the root `.prettierrc` (the same options as the SPA config, Angular parser
for HTML included): the source-shared libs `libs/i18n`, `libs/web-ui`, `libs/shared-utils` and
`libs/theme` through their own `format` / `format:check` targets, and the files outside every
project (`scripts/**/*.mjs`, the acceptance-case data `docs/testing/*.ts`) through the `libs/i18n`
target, whose Nx `inputs` (the `nx` block in `libs/i18n/package.json`) name those out-of-root
globs. The pre-commit hook formats all of them through the `extra` entries of
`lint-staged.config.mjs`. `libs/api-client` and `libs/api-types` are generated and never
formatted by hand. **`console.log` fails lint** in every project with an ESLint config (the
shared presets ship `no-console` as an error; `warn`/`error` stay allowed); the API logs through
Nest's `Logger`.

Run from the monorepo root (all fan out through Nx with caching):

- `pnpm lint` — lint all apps (or `pnpm lint:api` / `pnpm lint:spa`)
- `pnpm format` — format all projects (or `pnpm format:api` / `pnpm format:spa`)
- `pnpm format:check` — CI-friendly check (no writes)
- `pnpm build` — build all apps; `pnpm affected` — lint/build only what changed vs `main`
  (`hassan-devkit ci:affected`; `docs/`, `*.md` and translation catalogs never count — the
  `ci.affected.contentOnly` globs in the root `package.json` — while `ci.affected.adopted` maps
  `scripts/**/*.mjs` and `docs/testing/*.ts` to `tpl-i18n`, whose `format:check` reads them)
- Single-project targets: `pnpm exec nx run api:lint`, `pnpm exec nx run web-admin:build`, …
- **The pre-commit hook never rewrites silently.** When `prettier --write` / `eslint --fix` changed
  the staged tree the commit is ABORTED and the rewritten files are listed: review them
  (`git diff --cached`), rebuild what they touch, then run the same `git commit` again.
- **Pre-push parity** is the house rule (`pnpm ci:check` + `pnpm affected`). The
  path-triggered gates here are `check-translations` and `api:types:check` (`ci.checks` in
  the root `package.json`), and the affected builds are PRODUCTION builds: the dev-server
  compile skips the bundle **budgets** in each app's `angular.json` (initial ≤ 1.2MB error /
  1MB warning), so a change can pass lint locally and still fail CI.

## Testing policy: no unit tests

The house rule applies (no unit-test gate, acceptance cases are the gate, every user-facing
change ships its cases). The workspace has no unit-test tooling at all — don't add any. For
day-to-day editing in VSCode, open `template.code-workspace` so each app becomes its own root and
the correct formatter/linter resolves per file.

## Acceptance Test Cases

The case data lives in `docs/testing/tc-data-<suite>.ts`, one file per app (`web-admin`,
`web-customer`), in English and Dutch; `pnpm test-cases:generate` writes the gitignored
`test-cases-<suite>-<lang>.xlsx` workbooks next to them. Rules on top of the house procedure:

- Every case needs a title, preconditions, steps and expected results in both languages — the
  data files build cases with the devkit's `tc()`; continue the area's ID sequence (e.g.
  `SH-03`); update cases the change invalidated.
- A language the app gains joins `testCases.languages` in the root `package.json` only once the
  devkit's workbook generator ships its sheet labels (`en` and `nl` today).
