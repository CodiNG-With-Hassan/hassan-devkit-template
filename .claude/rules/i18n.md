## Shared translations (`libs/i18n`)

Framework-agnostic i18n shared by every web app (package `tpl-i18n`, consumed as source): the
`SUPPORTED_LANGUAGES` list (`en`, `nl`; `en` is the fallback) with the `LANGUAGE_OPTIONS` the
language switcher lists, and the `ERRORS` catalog + `toErrorTranslation` (ADR 0002). Labels of API enums will live here too, each
with a `*Key()` helper that builds its key. Rule: **labels of API enums live once in `libs/i18n`;
feature UI copy stays in the app's own `assets/i18n`** — never re-translate an enum value in an
app catalog, and never build a translation key by concatenating a wire value
(`'PREFIX.' + status.toUpperCase()`): use the shared `*Key()` helper, or for a label only one app
shows a `Record<union, string>` map exhaustive over the generated union (the full rule:
`libs/i18n/README.md`). App-local feature copy follows the same "Register per language" table as
`ERRORS` (`libs/i18n/README.md`). Each catalog folder under `libs/i18n/src/` is served through an
`angular.json` assets glob (`node_modules/tpl-i18n/src/<catalog>` → `assets/i18n/<catalog>`) plus
a module entry in the app's translate loader, whose `version` is the shared frozen
`I18N_CATALOG_VERSION` (`libs/i18n/src/catalog-version.ts`). Source packages imported by name
(`tpl-i18n`, `shared-utils`) must stay in `prebundle.exclude` of every app's `serve` target, or the dev server
exits (why: `libs/i18n/README.md`). Adding a language or key means a file per supported language
(`en`, `nl`) — `pnpm exec nx run-many -t check-translations` enforces parity
(`scripts/check-shared-translations.mjs` for the nested catalogs,
`scripts/check-error-translations.mjs` for `ERRORS` plus the error-contract mirrors — see
`api-errors.md`). App-local catalogs (`apps/<app>/public/assets/i18n`) get the same parity check
from `scripts/check-app-translations.mjs` through the app's own `check-translations` script in its
`package.json` — every app that ships catalogs must have one (the pre-commit hook rejects catalogs
without it), and the CI change filter covers every `apps/*/{public,src}/assets/i18n/` path.
`SUPPORTED_LANGUAGES` in `libs/i18n/src/index.ts` is the one language list: the web apps register
it (`translate.addLangs([...SUPPORTED_LANGUAGES])`, never a hardcoded array) and the API mirrors
it in `apps/api/src/common/supported-languages.ts` (same entries, same order — the check fails on
drift). See `libs/i18n/README.md`.

## Languages in the apps

Both web apps ship in every `SUPPORTED_LANGUAGES` entry. The language switcher (`@WebUi`) saves
the choice on the device (`LANGUAGE_STORAGE_KEY` from `@WebUi`); each app applies it at bootstrap
(`app.config.ts`) and keeps `<html lang>` in step. `web-customer` renders on the server, which has
no device storage: the server always renders the default language and the browser applies the
saved one at hydration. All UI copy goes through the catalogs and the `translate` pipe — never
hardcode text in a template. Lay out with **logical** properties (Tailwind `ms-*`/`me-*`,
`ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`/`text-end`), never the left/right utilities, so a
right-to-left language needs translated catalogs and a `dir` switch, not a rewrite.

Adding a language: the entry in `SUPPORTED_LANGUAGES` and `LANGUAGE_OPTIONS`
(`libs/i18n/src/index.ts`), the API mirror, a file in every catalog folder (shared and per app),
its row in the "Register per language" table of `libs/i18n/README.md`, and the acceptance cases
in that language once the devkit's workbook generator ships its sheet labels.
